# LLM Markdown 输出与 TTS 播报文本处理设计

## 1. 背景

LLM 返回的内容主要面向文本界面，可能包含 Markdown 标记，例如：

- `## 标题`
- `**重点内容**`
- `` `代码` ``
- `[链接文字](https://example.com)`
- 列表标记、代码围栏和换行符

这些内容如果原样送入 TTS，模型可能会把井号、星号、反引号、链接地址或换行控制字符读出来，影响播报质量。

当前共享 LLM → TTS 管线在 [crates/voice_server/src/pipeline/llm_tts.rs](../../../crates/voice_server/src/pipeline/llm_tts.rs) 中将原始 LLM delta 写入 `sentence_buf`，切句后直接调用 `tts.synthesize`。末尾残余文本也走同样的 TTS 调用路径。

## 2. 目标与非目标

### 目标

1. 保留原始 LLM 文本给前端展示或 Markdown 渲染。
2. 为 TTS 单独生成适合直接朗读的纯文本。
3. 清除 Markdown 结构符号、无意义控制字符和链接地址等不应播报的内容。
4. 过滤 LLM 输出中的 Unicode emoji，避免 TTS 尝试朗读表情名称或残留不可见组合字符。
5. 减少过短音频片段：切出的单个句子少于 5 个有效字符时，不立即调用 TTS，而是与后续句子合并后再调用。
6. 任何入口都遵循同一套播报文本规则，避免共享管线和管理接口行为不一致。

### 非目标

- 不修改前端展示文本的 Markdown 能力。
- 不改变 LLM provider 的输出协议。
- 不通过正则强行改写所有标点或重写用户原文语义。

## 3. 总体方案

LLM 输出分成两条路径：

```text
LLM delta
   ├── 原始 delta ──> 前端消息展示 / Markdown 渲染
   └── sentence_buf ──> 完整句子 ──> Markdown 清洗 ──> 短句合并 ──> TTS
```

服务端新增一个纯函数形式的播报文本处理层，例如 `to_tts_text(input: &str) -> String`。该函数只服务于 TTS，不修改向前端透出的 `LlmTtsItem::Llm { delta, .. }`。

清洗应在完整句子或完整段落上执行，而不是对每个流式 delta 单独执行。这样可以避免 Markdown 标记被拆在多个 delta 中时产生错误结果。

## 4. Markdown 清洗规则

理想情况下可使用 Markdown parser 解析结构，再提取可朗读文本；不建议只使用一组正则表达式，因为正则难以正确处理嵌套格式、链接、代码围栏和跨行结构。当前项目为避免引入新的运行时依赖，采用受控的轻量扫描器实现同一组明确规则；后续若 Markdown 语法范围扩大，可替换为 parser，调用方接口保持不变。

| 输入 | TTS 文本 |
| --- | --- |
| `## 使用说明` | `使用说明` |
| `**重要**` / `*重要*` | `重要` |
| `` `status` `` | `status` |
| `[帮助文档](url)` | `帮助文档` |
| `![截图](url)` | `截图`，或按产品策略忽略图片 |
| `- 第一项` / `1. 第一项` | `第一项` |
| `---` | 删除 |
| HTML 标签 | 删除标签，保留可见文本 |
| `😊`、`👍`、`👨‍💻`、`✅` 等 emoji | 删除 emoji 基础字符及变体选择符、肤色修饰符、ZWJ 组合字符 |
| 实际换行、字面量 `\\n`、异常的 `/n` | 转为空格或自然停顿 |

代码块需要单独定策略：语音助手默认建议跳过 fenced code block，或只播报“代码内容已省略”。如果产品必须播报代码，则需要维护代码围栏状态，不能只依赖当前按句末标点切分的逻辑。

清洗后应执行 `trim` 和空文本判断；清洗结果为空时不调用 TTS。

## 5. 短句合并优化

### 5.1 规则

对每个切出的完整句子执行清洗后，再判断其长度：

1. 统计清洗后的 Unicode 有效字符数，忽略空白和 Markdown 结构符号；标点不作为有效字符计数。
2. 有效字符数少于 5 时，放入 `pending_tts_text`，不立即调用 TTS。
3. 下一个句子切出并清洗后，与 `pending_tts_text` 拼接，中间保留一个自然分隔（通常是空格或原句末标点后的空白）。
4. 合并后的文本达到至少 5 个有效字符时，作为一次 TTS 请求发送，并清空 `pending_tts_text`。
5. 如果连续多个句子都很短，持续合并，直到达到阈值或 LLM 流结束。

示例：

```text
“好的。”       2 个有效字符，暂存
“我马上处理。” 5 个以上有效字符
=> 合并为一次 TTS：“好的。我马上处理。”
```

### 5.2 流结束兜底

LLM 流结束后，如果 `pending_tts_text` 仍有内容，即使少于 5 个有效字符，也必须发送一次 TTS。不能因为没有下一个句子而丢弃用户可见的回答内容。

同理，末尾没有句末标点的 `tail` 需要先加入短句缓冲，再执行一次最终 flush。

### 5.3 与现有切句逻辑的关系

短句合并应位于 `next_sentence_end` 切句之后、`tts.synthesize` 之前，不改变现有句末标点识别逻辑，也不改变全局音频 `seq` 编号和 crossfade 行为。

推荐的处理顺序为：

```text
切出句子
  -> to_tts_text
  -> 空文本过滤
  -> pending_tts_text 短句合并
  -> tts.synthesize
  -> crossfade / seq 编号 / 下发音频
```

## 6. 代码落点

### 6.1 共享 LLM → TTS 管线

在 `crates/voice_server/src/pipeline/llm_tts.rs` 中：

- 原始 `evt.delta` 继续通过 `LlmTtsItem::Llm` 原样透出。
- `sent` 不直接传给 `tts.synthesize`，改为先经过 `to_tts_text` 和短句合并逻辑。
- `tail` 使用同一套清洗和 flush 逻辑。
- 保持现有 TTS 错误码、取消机制、crossfade 和结束标记不变。

### 6.2 其他 TTS 入口

`/admin/tts` 等直接接受文本的入口也应复用 `to_tts_text`，使所有服务端 TTS 请求都具备相同的兜底能力。前端显示路径不调用该函数。

### 6.3 提示词辅助约束

在 system prompt 中补充语音场景约束：

```text
这是语音对话，请只输出适合直接朗读的纯文本，不要使用 Markdown 标题、列表、加粗、代码块、链接格式或特殊排版符号。
```

该约束只能降低 Markdown 输出概率，不能替代服务端清洗。

## 7. 错误处理与边界

- 清洗后为空：跳过 TTS，但仍保留原始 LLM 文本事件。
- emoji 过滤只作用于 TTS 文本，原始 LLM 文本事件仍保留 emoji，前端可继续展示。
- TTS 调用失败：沿用现有错误码和终止行为。
- 用户打断：清空当前短句缓冲，不发送被取消请求的残余文本。
- Markdown 标记跨 delta：必须先累计到可处理边界，再清洗。
- 长代码块：默认不播报代码内容，避免句末切分把代码片段送入 TTS。
- 只有短文本且流结束：执行最终 flush，不能静默丢失回答。

## 8. 测试验收标准

### 清洗函数

- 标题、粗体、斜体、行内代码不会播报 Markdown 符号。
- 普通 emoji、带变体选择符的 emoji 和 ZWJ 组合 emoji 不会进入 TTS 请求。
- 链接只播报链接文字，不播报 URL。
- 列表序号和项目符号不会被播报。
- 实际换行、`\\n` 和 `/n` 不会作为控制字符污染 TTS 文本。
- 代码围栏按既定策略被跳过或转换为固定提示。
- 清洗后为空时返回空字符串。

### 短句合并

- 少于 5 个有效字符的句子不会立即调用 TTS。
- 后续句子到达并达到阈值后，只调用一次 TTS，内容顺序正确。
- 连续多个短句会持续累积，不会丢句或重复播报。
- 流结束时未达到阈值的残余文本仍会被发送一次。
- 合并后的 TTS 请求仍按原有顺序产生音频，`seq` 连续递增。
- 原始 `llm_delta` 事件内容不被清洗，前端仍可正常渲染 Markdown。

## 9. 验收示例

输入：

```markdown
## 今天的安排

**好的。**

我会先处理第一项，然后同步结果。\n
```

前端展示：保留原始 Markdown。

TTS 请求文本应接近：

```text
今天的安排 好的。我会先处理第一项，然后同步结果。
```

其中 `好的。` 不单独调用 TTS，而是与后续句子合并后发送。
